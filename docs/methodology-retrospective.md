발표자료용 정리. 커밋/문서 기반 재구성이며, **그릴링 세션의 실제 대화 로그는 남아있지 않다** —

역추적 가능하다. 이 문서의 한계로 미리 밝혀둔다.

## 0. 방법론 스택

`.agents/skills/`는 `mattpocock/skills`(GitHub) 원본을 그대로 vendoring한 것 —
`skills-lock.json`에 소스·해시가 박제됨(`0e02c0e`). 표준 파이프라인:

```
grilling(=grill-me)  →  to-spec(구 to-prd)  →  to-tickets(구 to-issue)  →  implement  →  code-review  →  handoff
   결정 인터뷰            PRD 합성                티켓 분해                 구현+테스트    2축 리뷰       다음 세션 인계
```

- `setup-matt-pocock-skills`가 만드는 정식 부트스트랩 산출물(`docs/agents/issue-tracker.md` 등)은
  이 저장소에 **없다** — 파이프라인은 공식 설정 없이 관례로 재현됨.
- 스킬이 리포에 커밋되기(`0e02c0e`, 04:56) **전에** 이미 PRD가 작성돼 있었다(`f0b0e2a`, 04:36) —
  즉 방법론은 개인/글로벌 설치본으로 먼저 쓰이고, 나중에 재현성을 위해 저장소에 박제됐다.

## 2. 변곡점 타임라인

### 변곡점 1 — `handoff` → `grill-me` 예고 (브레인스토밍 → 사양 확정)

`docs/deprecated/2분기회.md`(초기 메모) 다음에 나온 `분기회-AI세그먼트-사양확정.md`는
그 자체가 **`/handoff` 스킬의 산출물**이다 — 문서 끝의 `## 10. Suggested skills (다음 세션용)`이
스킬 정의가 요구하는 "suggested skills 섹션"과 정확히 일치:

```
- to-prd: 사용자가 PRD 요청 시 사용
- grill-me: 미정 사항(문항 설계 등) 구체화 시 스트레스 테스트용
```

**요구사항 정제 관점의 아쉬움**: 이 단계에서 실제로 그릴링이 몇 번, 어떤 질문으로 진행됐는지의
기록은 없다. 남은 건 "사양 확정"이라는 결과뿐 — 과정은 유실됨.

### 변곡점 2 — `to-prd`/`to-spec` 실행 → PRD 확정

`docs/PRD-heritage-archive.md`의 섹션 구성(Problem Statement / Solution / User Stories 40개 /
Implementation Decisions / Testing Decisions / Out of Scope / Further Notes)이 `to-spec` 스킬의
`<spec-template>`과 **1:1 일치**. User Story 포맷(`As <actor>, I want <feature>, so that <benefit>`)도
스킬 지시를 문자 그대로 따름.

### 변곡점 3 — `to-tickets`(구 to-issue) → `todos/001~009`, Phase 1 구현

001(더미 데이터+빌드 조립, 프리팩터)이 스키마를 고정하자 002~007이 병렬 진행(`todos/README.md`
스스로 이렇게 설명) — `to-tickets`가 요구하는 "tracer-bullet vertical slice + blocking edges"
그대로. 단, 스킬 원본 템플릿에 YAML frontmatter(`id/status/blocked_by/labels`)를 추가한
**하이브리드 포맷으로 변형**해서 사용 — 스킬을 곧이곧대로 따르기보다 필요에 맞게 편집.

### 변곡점 4 — UX 폭풍, 인터랙션 모델 붕괴와 재수렴 (2026-07-12~13)

가장 커밋이 밀집된 구간. 클릭=dim/더블클릭=isolate → 스코프 탭 4종 → 유사군 자동연동까지
시도했다가 전부 폐기하고 **원클릭 단일 모델**(팀 클릭=그 팀만, 다시클릭/빈공간=전체)로 수렴
(`c0cc7f5`). 원칙: **"만든 사람(Jay)도 못 외우는 인터랙션은 버그"** — PRD의
"사양 변경 이력(2026-07-13)"으로 공식 문서화됨. `e6b10df`("코드 리뷰 반영") 커밋이
`code-review` 스킬 실행의 첫 명시적 흔적.

이 구간에 Gemini 쿼터 문제로 내부 LLM(OpenAI Compatible API) 지원으로 전환하는 결정도 포함
(`e5fd512`~`21ddf9b`) — 요구사항이 아니라 인프라 제약이 만든 변곡점.

### 변곡점 5 — 실데이터 파이프라인 사고 (2026-07-13~14)

`docs/handoff-2026-07-13.md`. PPT→MD 분할 스크립트가 **전원 "이상" 판정**을 낸 사고. 원인은
파일 분할 경계에서 `cat`으로 합쳐 처리하다 배정이 밀린 것. 해법은 **"재설계가 아니라 입력
프로세스 수정"** — 물리 파일별로 따로 처리. 매니페스트도 CSV→sqlite(`roster.db`)로 전환
(사내망 DRM이 `.csv`를 차단하는 문제 회피).

**코드 저장소에는 안 남는 어려움 — docpamin 100MB 제한과 이름 매핑 노가다**: 이 구간에서
커밋 로그·테스트로는 안 보이는, 실제로 가장 손이 많이 간 부분.

- **docpamin(사내 PPT 파서) 100MB 제한**: 근원경쟁력 원본 PPT 중 용량이 큰 파일(`cl2_y5-8` 등)이
  docpamin 처리 한계(100MB)를 넘겨, 파일을 물리적으로 나눠야 했다. `_1.md`/`_2.md` 같은 분할
  산출물이 그 흔적(`docs/handoff-2026-07-13.md`의 "용량 문제로 분할된 파일" 언급). 이 분할은
  스크립트가 자동으로 한 게 아니라 **파일을 자르는 것 자체가 수작업**이었고, 이후 이 분할 파일들을
  `cat`으로 합쳐 처리하려다 사람 배정이 밀리는 버그(위 "전원 이상" 판정 사고)로 이어졌다.
- **사람 이름에 대한 확실한 정보 부재**: docpamin이 뽑아낸 텍스트만으로는 "이 페이지가 누구 것인지"를
  신뢰도 있게 자동 매핑할 수 없었다. 페이지 하단에 이름이 있다는 규칙은 있었지만 표지·목차·분할
  경계 등 예외가 많아, **실제로 원본 PPT를 페이지 단위로 직접 넘겨보며 "이 페이지 구간은 누구"
  식으로 로스터(`master.json` → 이후 `roster.db`)에 사람별 페이지 범위를 수기로 채워 넣는 작업**이
  필요했다.
- 이 수작업이 **2026-07-13~14 구간에서 가장 노가다가 심했던 부분**이다 — 커밋으로는
  `698cd9f`(CSV→JSON), `3239f4d`(sqlite 통합), `e5af14e`(페이지 구분자 확정) 정도의 흔적만
  남지만, 실 소요 시간은 스크립트 작성이 아니라 **PPT를 직접 눈으로 훑으며 이름-페이지를
  맞추는 검수**에 있었다. `data/roster.db` 자체도 gitignore돼 있어 이 작업의 산출물조차 코드
  저장소에는 남지 않는다.
- 완전 자동화하지 않은 이유: 문서마다 이름 표기·위치가 미묘하게 달라 자동 매핑의 신뢰도가
  낮았고, 150~238명 규모에서는 사람이 한 번 눈으로 훑는 편이 오배정 재작업 위험보다 저렴하다고
  판단했다.

### 변곡점 7 — 방향 전환: 발표 후 `grilling` 재등장, task-discovery 설계 (2026-07-16)

발표 종료 직후 첫 행동은 코드가 아니라 **다시 그릴링**. `docs/task-discovery.md`의
"결정과 기각" 섹션이 이 세션의 사후 압축본:

| 검토한 것 | 결론 |
|---|---|
| 사람 단위 군집 (기존 아카이브 방식 재사용) | **기각** — "AI가 과제를 창작"하는 것과 "팀원 N명이 실제로 쓴 과제"는 설득력이 다르다 |
| RAG 방식 | **기각** — 발굴 질문("전체 조망해 빈 곳 찾기")엔 검색어가 없다 |
| Karpathy식 순차 wiki 갱신 | **기각** — 순서 의존성. 배치 파이프라인 채택 |
| 자유 브레인스토밍형 생성층 | **기각** — 근거 없는 그럴듯한 과제 생성기가 됨 |

**요구사항 정제 관점의 핵심**: 여기서 가장 중요한 결정("사람 단위 기각 → 과제 문장 단위")은
프로젝트 전체 방향을 바꾼 변곡점인데, 이 결정에 이르기까지의 **질문-답변 과정 자체는 기록에 없다**.
남은 건 결론과 이유뿐 — 그릴링의 가치가 "왜"에 있다는 걸 알면서도 "왜"의 원본 대화는 이미
휘발된 상태. (설계 문서가 결과를 잘 정리했다는 것과, 정제 과정 자체가 재구성 가능하다는 것은 별개.)

## 3. `handoff`로 세션을 이어온 이력

이 저장소는 최소 8번의 명시적 `handoff` 지점을 거쳤다. 코드 커밋과 별개로, "세션이 끊기고
다음 세션이 이어받는" 경계마다 문서가 갱신된 흔적:

| 시점 | 커밋 | 문서 | 내용 |
|---|---|---|---|
| 2026-07-12 | `23fbd32` | `HANDOFF-gemini-api.md`(현 deprecated) | Gemini API 파이프라인 세션 인계 |
| 2026-07-13 04:36 | `f0b0e2a` | `handoff.md` 전면 재작성 | README 신규 + "현재 상태" 스냅샷으로 전환, PRD 사양 변경 이력 병기 |
| 2026-07-13 04:51 | `27fc173` | 구 handoff 3종 → `docs/deprecated/` | 낡은 핸드오프(사양확정·Gemini API·초기메모) 정리 |
| 2026-07-13~14 | `3239f4d` | `handoff-2026-07-13.md` 신규 | 실데이터 파이프라인(로스터+sqlite) 전용 상세 스냅샷 — 정본 `handoff.md`와 분리 |
| 2026-07-16 | `1bc5ab9` | `handoff.md` 갱신 | 발표 종료, task-discovery 방향 반영(다음 세션 예고) |

패턴: `handoff.md`는 **누적 append가 아니라 매번 "현재 상태"로 덮어써지는 스냅샷**이다 —
문서 1행이 "빌드·사용법은 README가 정본이고, 여기는 왜 이렇게 생겼는지와 함정을 남긴다"고
스스로 선언한다. 옛 결정의 배경은 문서에 다시 안 쓰고 git 히스토리로 되짚게 설계됨
(예: "v1 핸드오프 초기 요구사항 원문은 `e30e847` 이전 버전 참조") — `handoff` 스킬이 요구하는
"다른 산출물과 중복 금지, 경로/커밋으로 참조"가 실제로 지켜진 사례. 상세 이력이 필요한
국면(2026-07-13 실데이터 사고)만 예외적으로 별도 파일(`handoff-2026-07-13.md`)로 분리해
정본을 가볍게 유지했다.

## 4. 요구사항 정제(grilling) 부분의 한계 — 별도 정리

이 저장소에서 가장 중요한 방향 전환들(사람 단위→문장 단위, 우선순위 지표 보류, 두 지도 상태
분리)은 전부 **그릴링 세션에서 나왔다**고 문서가 명시하지만, 세션 자체의 질문-답변 기록은
어디에도 남아있지 않다. 있는 것은:

- 설계 문서의 "결정과 기각" 표 — **결론의 사후 요약**
- handoff 문서의 "왜 이렇게 됐는지" 서술 — **역시 사후 요약**

즉 "왜 이 질문을 던졌고, Jay가 어떤 대안들 사이에서 왜 이걸 골랐는가"의 원본 서사는
복원 불가능하다. 발표자료에서 이 부분을 다룰 땐 "그릴링이 있었다"는 사실과 "그 결과"까지만
말할 수 있고, 과정을 극적으로 재연하려 하면 안 됨 — 근거가 없다.

## 5. 발표용 핵심 메시지 후보

1. **"방법론이 코드보다 먼저 왔다"** — 스킬이 저장소에 커밋되기도 전에 이미 grill→spec→tickets를
   쓰고 있었고, 나중에 `skills-lock.json`으로 재현성을 박제.
2. **"만든 사람도 못 외우면 버그다"** — 3중 필터 UX가 원클릭 모델로 수렴한 이야기. 아카이브로
   영구 남는 물건이라는 제약이 단순화를 강제.
3. **"AI가 지어낸 과제 vs 팀원이 실제로 쓴 과제"** — task-discovery가 사람 단위 요약을 기각하고
   문장 단위 군집을 택한 이유. 설득력의 근원이 어디 있는지에 대한 철학.
4. **같은 교훈이 두 번 등장한다** — "필터 경로 두 개는 헷갈린다"(Phase 4)가 "두 지도는 상태
   미공유"(Phase 9)로 재적용됨. 문서화된 교훈이 실제로 재사용된 사례.
5. **정제 과정은 휘발되고 결론만 남는다** — 이 저장소의 가장 중요한 결정들이 전부 그릴링에서
   나왔다고 기록돼 있지만, 그 대화 자체는 사라졌다. "결정 로그는 남기되 과정은 놓친다"는
   흔한 실패 패턴의 실사례 — 다음 프로젝트에서 그릴링 세션 자체를 별도로 남기는 습관을
   고려해볼 지점.
