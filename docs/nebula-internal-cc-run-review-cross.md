## 교차 검증 결과 — 3개 관점별 의견 수렴

### 1. 구조적 타당성 → **전원 조건부 타당**

| 리뷰어 | 판정 | 핵심 |
|---|---|---|
| gpt-6-astra | 조건부 타당 | 파이프라인 계약 우회 없음, 재개 단위 작음. 단 **잠금 보장 설명 오류[치명]** — flock은 프로세스 수명만 잠김 |
| deepseek-v4-pro | 조건부 타당 | 오케스트레이터가 파일을 안 여는 설계 좋음. **보안 경계가 정책에만 의존[경고]** (프롬프트 인젝션) |
| glm-5.2 | 조건부 타당 | 보안·외부 의존 제거 좋음. **1워커 직렬 → 메인 대기 시간 문제[경고]** |
| devstral-2512 | 조건부 타당(치명 태그) | 무상태 루프 좋음. **race condition 위험[치명]** + 상태 관리 복잡성 |

→ **4/4 합의: 구조는 맞다. 단, '잠금이 워커 직렬성을 보장한다'는 CC의 설명은 코드와 다르다** (gpt-6-astra가 storage.py:46-68 근거로 치명 지적 — flock은 프로세스 수명만 유지, 워커의 답 작성 구간에는 잠금 없음). 문구 수정 + worker lease 필요.

→ 병목 완화 공통 제안: 답 30개 배치를 컨텍스트 상한에 맞게 축소(gpt-6-astra: 30턴이면 요청 본문만 72만 자 누적 가능[경고]) 또는 전원 tasks→taxonomy 스케줄 재구성.

### 3. 파이프라인 순서 → **extracted 먼저 맞다 (4/4 합의)**

- gpt-6-astra: taxonomy의 입력은 원문이 아니라 **검증된 미래 과제 목록** — taxonomy가 추출보다 앞설 수 없다. 단 '전원 tasks→taxonomy→나머지' 스케줄 최적화는 가능(운영 순서 문제일 뿐)
- deepseek/glm/devstral도 동일 결론 — 순서 자체는 설계상 정확함

## 공통 권고 (우선순위)

1. [치명] 문서의 잠금 설명 수정: "오케스트레이터는 동시에 한 워커만 활성화한다"로. 기술적 강제가 필요하면 worker lease 구현
2. [경고] 30개 배치 → 원문 24,000자 최대 계약 기준 컨텍스트 상한 검증. 초과 시 배치 축소
3. [경고] provider에 모델 미기록 → 품질 감사 불가. run.model_id 기록 절차 지키기(문서에 이미 있음)
4. [경고] 프롬프트 인젝션 방지: 원문이 워커 컨텍스트에 들어가므로, 계약 밖 보고 차단 규칙을 워커 프롬프트에 명시
5. [참고] 70명 완주 예상: 턴 지연 실측 먼저(합성 2명 리허설에서 측정) → 배치 크기 조정

## 종합

CC-direct 전환은 **구조적으로 맞는 선택**(파이프라인 계약 유지, 외부 의존 제거). 단, 문서의 잠금 설명 1건 수정이 선행되어야 하고, 70명은 리허설에서 턴 지연을 실측한 뒤 배치 크기를 정하는 것이 안전하다. 200명 상시 운영은 별도 설계(병렬 워커+lease)가 필요한 별개 과제다.
