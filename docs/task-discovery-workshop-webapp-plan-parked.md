# [구현 완료 · 기록용] 인터랙티브 워크숍 웹앱 — v1 계획 (2026-08-05 작성)

>
> **당시 미결이던 세 가지는 이렇게 정해졌다:**

>

> 매트릭스가 입력이 아니라 **투표의 산출**이 됐다.

## Context
상사 요구("근원경쟁력 기반 팀 10년 로드맵")를 다루려고 task-discovery 파이프라인
(`td_extract→taxonomy→assign→aggregate→render`, 최근에 Layer 2 `td_narrate` 추가)을
만들어왔다. 지금까지 산출물은 전부 **정적 문서**(workshop-input.md, interpretation/*.md,
Marp 슬라이드)였는데, Jay가 "이걸 기반으로 인터랙티브 워크숍을 해보면 어떨까 — 참석자가
투표하는 형태로"라는 아이디어를 냈다. 특히 이건 예전에 막혀 있던 문제 하나를 풀어준다:
`aggregates.json`에 우선순위/중요도를 알고리즘이 매기면 "가중치 근거가 뭐냐"는 시비가
생기는데, **워크숍 참석자가 그 자리에서 투표**하면 그 순위의 근거는 "우리가 투표했다"가
되어 시비 자체가 없어진다.

세 가지를 물어 답을 받았다:
- **디바이스**: 사내망에서 참석자 각자 PC/브라우저로 접속(공유화면 1대 아님) — 그래서
  투표를 취합할 서버가 필요하다. DB까지 필요하냐고 되물었음 → 이 계획에서 "아니다,
  파일 영속화로 충분하다"고 답함(아래 근거).
- **투표 대상**: "LLM 결과 보고 나서 기획해야 할 듯" — 지금 확정하지 않는다. 그래서
  이 계획은 투표 대상을 하드코딩하지 않고, Layer 1 산출물의 **어떤 목록이든** 투표
  대상으로 얹을 수 있는 일반화된 구조로 간다.
- **스키마 범위**: "고민 중, 추천해달라" → **Layer 1만**을 v1 범위로 추천한다. 이유는
  아래 "스키마 범위 추천" 참고.

## 스키마 범위 추천: Layer 1만 (v1)

- Layer 1(`taxonomy.json`/`assignments.json`/`aggregates.json`)은 이번 세션까지 테스트
  151개로 검증됐고, 사내망 taxonomy 생성도 1차로 확인된 유일한 "안정적인" 산출물이다.
- Layer 2(`td_narrate.py`/`interpretation/`)는 이번 세션에 막 착수했고, 스코프(총평만
  vs 카테고리 페이지까지)가 아직 회의로 확정 안 됐다 — 불안정한 것 위에 새 웹앱을
  얹으면 두 가지가 동시에 흔들린다.
- 데이터 모델을 일반화해두면(아래) Layer 2가 확정된 뒤 "투표 대상 소스"를 하나 더
  추가하는 것만으로 확장 가능 — 지금 Layer 1만으로 시작해도 나중에 다시 설계할 필요 없음.

## 아키텍처 — 왜 이렇게 짜는지

**서버가 필요한 이유**: 참석자 각자 디바이스에서 투표하면 그 결과를 한 곳에 모아 실시간
집계해서 다시 보여줘야 한다. Heritage Archive처럼 완전 정적 파일로는 안 됨 — 이건 이
프로젝트에서 처음 등장하는 "여러 클라이언트가 상태를 공유하는" 요구다.

**DB는 필요 없다.** 워크숍은 사내망에서 한 세션(몇 시간)짜리 1회성 이벤트고, 참석자는
많아야 수십 명, 투표 항목도 Layer 1 카테고리 수(15~25개) 규모다. 이 프로젝트 전체의
기존 철학("순차 루프+재시도+**파일 영속화**로 충분, 오케스트레이션 프레임워크 미도입")을
그대로 따르면: **서버 프로세스 메모리에 집계 상태를 들고, 투표가 들어올 때마다 JSON
파일로 write-through**하면 충분하다. 서버가 죽어도 마지막 상태가 파일에 있어서 재시작하면
복구된다. SQLite조차 이 규모·수명에는 과설계다.

**새 의존성은 추가하지 않는다.** `requirements.txt`엔 웹 프레임워크가 전혀 없다(pytest/
kiwipiepy/google-generativeai/openai뿐). 엔드포인트가 3개(`GET /state`, `POST /vote`,
정적 파일 서빙)뿐이라 Flask 같은 프레임워크 없이 **표준 라이브러리
`http.server.ThreadingHTTPServer` + 커스텀 핸들러**로 충분하다 — 새 패키지 0개.
(참고로 이건 이 계획에서 유일하게 "프레임워크를 안 쓴다"는 선택을 사람이 재확인해줬으면
하는 지점이다 — 나중 단계에서 실시간성이 부족하다고 느끼면 그때 재검토.)

**프런트엔드**: `dist/heritage-archive.html`과 같은 패턴 — 단일 정적 HTML, 바닐라 JS,
빌드 스텝 없음. `GET /state`를 3초 간격으로 폴링해서 집계를 갱신, 클릭하면 `POST /vote`.
WebSocket 대신 폴링을 쓰는 이유: 참석자 수·갱신 빈도가 낮아 폴링으로 충분하고, 소켓
서버보다 구현·디버깅이 훨씬 단순하다(재연결 처리 등 신경 쓸 게 없음).

## 데이터 모델 (투표 대상 미확정을 흡수하는 설계)

투표 대상을 코드에 하드코딩하지 않는다. 서버 시작 시 "어떤 Layer 1 목록을 투표 대상으로
쓸지"를 설정 하나로 받는다:

```
{item_id, label, source}   # source: "category" | "relation" | "minority" (나중에 추가 가능)
```

v1은 `source="category"`만 채워 넣는다(`aggregates.json`의 `categories[]`를 그대로
item으로 변환 — name을 label로). 나중에 관계 승인이나 소수의견 투표가 필요해지면
같은 구조에 `source="relation"` 항목을 추가하는 것만으로 확장된다(서버·프런트 코드
변경 없음, 데이터 로더만 확장).

집계 상태:
```
{item_id: {option: count}}   # option은 투표 종류에 따라 다름(예: "찬성/반대", 1~5점 등 미정)
```
**투표의 "옵션 종류"(찬성/반대 vs 순위 매기기 vs 별점)는 여전히 미확정** — Jay가 LLM
결과를 보고 정하겠다고 했으므로, v1 구현 시작 시점에 다시 확인이 필요하다. 이 계획은
그 결정이 나기 전까지 구현에 들어가지 않는다(아래 "다음 결정 지점" 참고).

## 파일 계획

- `scripts/workshop_server.py` (신규) — `http.server` 기반, `GET /state`·`POST /vote`·
  정적 파일 서빙. `aggregates.json`을 읽어 초기 item 목록 구성. 투표는
  `data/task_discovery/workshop-votes.json`에 write-through(gitignore 대상, 기존
  `data/` 컨벤션 그대로).
- `dist/workshop/` 또는 별도 디렉터리(신규, 배포 대상 아님 — 사내망 로컬 실행용이라
  `dist/`에 넣을지도 재확인 필요) — 단일 HTML, 바닐라 JS. 매트릭스뷰/온톨로지 그래프뷰
  SVG 목업(`docs/task-discovery-overview-slides.md`에 있던 것)과 톤을 맞춰
  버블/카드 형태로 항목을 보여주고 클릭하면 투표.
- `tests/test_workshop_server.py` (신규) — 서버의 순수 로직 부분(집계 갱신, 파일
  write-through, item 목록 구성)을 함수 단위로 테스트. HTTP 계층 자체는 최소한만
  (요청 하나 보내서 응답 검증하는 스모크 1~2개) — 이 프로젝트의 기존 테스트 철학
  ("순수 함수 + 주입된 call/seam")을 그대로 따른다.
