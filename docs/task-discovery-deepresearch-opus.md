# task-discovery — 근원경쟁력 회고 기반 로드맵 원재료 추출 설계

## 〖 1. 요구사항 〗

상사 구두 전달 (2026-07-24), 원문 전부:

> 우리 팀 사람들이 쓴 근원경쟁력 기반으로, 우리 팀의 꿈이 담긴 향후 10년 로드맵

해석:
- **"10년"은 문자 그대로가 아닌 프레임.** 용도는 확정 실행계획이 아니라 리더십 토론 촉발로 추정(미확인).
- **본 과제의 산출물은 로드맵이 아니라 로드맵 워크숍의 입력물.** 근거는 §3 T-Plan, §4 제약 1.

## 〖 2. 입력 데이터 〗

부서원 ~200명이 작성한 근원경쟁력 회고. **1회성 수집** (분기 반복 아님).

| 필드 | 내용 |
|------|------|
| `name` | 실명 |
| `cl_level` | CL2 / CL3 / CL4 |
| `pjt` | 담당 프로젝트/파트 |
| `text` | PPT 원문 (회고 본문) |

### CL별 문서 구성

- **CL2 / CL3** — 3단 구성이 원칙: ① 상반기 성과·하반기 전략 ② 커리어 회고·확보 역량 ③ 미래 업무.
  원칙일 뿐 **미준수 문서 혼재**.
- **CL4** — 미래 위주 서술형 템플릿.

## 〖 3. 제약 〗

1. **데이터에 로드맵 자체는 없다.** 회고는 상향식·개인·근미래(1~3년) 과제/역량이다. 10년·시퀀싱·전략·"꿈"은 데이터에 없고 *원재료*(방향·역량갭·momentum)만 있다. 없는 것을 생성하지 않는다.
2. **실데이터 외부 반출 불가.** 원문을 보며 튜닝할 수 없는 상태에서 설계·검증해야 한다.
3. **추출이 sparse·노이즈를 견뎌야 한다.** 3단 미준수, 무내용("열심히 하겠습니다")류 문서 포함.
4. **규모·비용.** ~200명, PPT 원문 장문 가능(청킹 필요). 레이트 리밋·실패 폐기 처리 필요.

### 가용 인프라
- Elasticsearch — kNN 벡터 + BM25 + nori 형태소 분석
- 임베딩 — 내부망 BGE-M3 (OpenAI-compatible)
- 생성 LLM — 내부망 OpenAI-compatible 서버(예: Ollama), 모델 후보 미확정

## 〖 4. 조사 — 재활용할 기성 방법론 〗

밑바닥 설계 대신 기성 방법론 4개를 차용한다.

### 4.1 Clio (Anthropic, 2024)
파이프라인이 본 과제와 동형. 원문에서 facet(속성)을 추출 → facet을 임베딩해 클러스터링 → 클러스터에 제목·요약 부여 → 계층화. **개인 원문을 사람이 열람하지 않고도 집계 인사이트가 나오는 구조** = 제약 2와 맞음.
→ https://www.anthropic.com/research/clio / arXiv:2412.13678
**오픈소스 아님. 코드가 아니라 패턴을 가져온다.**

### 4.2 TnT-LLM (Microsoft, KDD 2024)
각 문서를 LLM으로 요약한 뒤, 요약들로부터 taxonomy를 배치 반복으로 생성·갱신. 라벨을 원문에서 추출하지 않고 서술형으로 생성하며 seed 라벨이 불필요.
**노이즈 대응 장치가 여기 있음** — 할당 프롬프트에 `Other/Undefined` 범주를 두고 그 비율로 taxonomy 커버리지를 측정. 무내용 문서가 억지 분류되지 않고 격리된다.
→ arXiv:2403.12173 / dl.acm.org/doi/10.1145/3637528.3671647
**오픈소스 아님. 알고리즘·프롬프트 구조를 구현한다.**

### 4.3 BERTopic
임베딩 + HDBSCAN + c-TF-IDF 토픽 모델링.
**채택하지 않음** — 임베딩은 내부 BGE-M3, 클러스터링은 sklearn/hdbscan으로 대체되고 남는 건 c-TF-IDF 라벨 후보뿐인데 그건 LLM 명명으로 대체된다. 의존성·외부망 리스크만 늘어난다(§6.1).

### 4.4 T-Plan (Cambridge IfM, Phaal et al.)
로드맵 층 구조. 상위층 = 목적(know-why), 중간층 = 전달 수단(know-what), 하위층 = 역량·기술(know-how). 표준 프로세스는 층별 워크숍 3회 + 시간축 통합 워크숍 1회.
→ https://www.ifm.eng.cam.ac.uk/insights/roadmapping/t-plan/ / Phaal et al., TFSC 71(2004) 5-26

**→ 제약 1 충돌의 구조적 해소:** 회고 데이터는 know-how / know-what 층 재료만 담는다. know-why("꿈")와 시간축은 통합 워크숍에서 리더십이 채운다. 본 과제를 워크숍 입력물로 정의하면, 없는 것을 지어내지 않고도 요구사항 경로가 닫힌다.

## 〖 5. 설계 — 파이프라인 〗

### 5.1 분할
CL2/3은 3단 구성 경계가 자연 청킹 단위(성과 / 역량 / 미래). CL4는 서술형이므로 길이 기준 분할. 섹션 라벨을 메타데이터로 유지.

### 5.2 facet 추출 (인당 1~2콜, JSON)
```
capability_have[]   확보 역량
capability_gap[]    부족·필요 역량
future_task[]       미래 업무
direction           지향 방향 1문장
substantive         무내용 판정 플래그 (false = "열심히 하겠습니다"류)
```
항목별로 `evidence`(원문 span), `confidence` 부착.

### 5.3 정규화
표기 변형 병합. ES kNN(BGE-M3) 코사인 임계 + nori 기반 BM25 이중 확인으로 동의 표현 통합.

### 5.4 클러스터링 + 명명
**문서 단위가 아니라 facet 단위**로 클러스터링 → TnT-LLM식 배치 반복으로 역량 taxonomy 생성, `Other` 범주 유지.

### 5.5 교차 집계
클러스터 × `cl_level` × `pjt`. 지표는 단순 개수가 아니라 **확산도** — 몇 개 pjt에서, 몇 개 CL에서 동시 출현했는지.

| 패턴 | 해석 |
|------|------|
| 전 파트 공통 출현 | 조직 신호 |
| 단일 pjt 집중 | 국소 과제 |
| 소수 선행 언급 | weak signal |

### 5.6 시간축 대체
10년 축을 만들지 않는다(데이터에 없음). 대신 **준비도 3구간**으로 대체:

- `이미 함` — have 다수
- `갭만 있음` — gap 다수, have 희박
- `선행 신호` — 소수 언급

리더십이 이 축을 연차로 번역한다.

## 〖 6. 내부망 적합성 〗

전 단계가 내부망에서 완결된다. 원문은 어느 단계에서도 외부로 나가지 않는다.

### 필요 스택 (전부 pip)
`httpx`/`openai` (내부 LLM·BGE-M3) · `elasticsearch` · `scikit-learn` + `hdbscan` · `numpy` · `pandas` · `jinja2`

### 6.1 외부망 접촉이 생기는 지점 — 차단 필요

| 지점 | 대응 |
|------|------|
| 모델 가중치 자동 다운로드 (`sentence-transformers`/`transformers`, BERTopic 기본값이 HuggingFace를 때림) | 해당 패키지 미사용. 부득이하면 `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` |
| 한국어 토크나이징 (konlpy = JVM·사전 다운로드) | **ES `_analyze` API + nori**. 추가 설치 0 |
| 프레임워크 텔레메트리 (LangChain/LangGraph 트레이싱) | 오케스트레이션 프레임워크 자체가 불필요. 순차 루프 + 재시도 큐로 충분 |
| 산출 HTML의 CDN 의존 (plotly.js 등) | JS 인라인 임베드 |
| pip 설치 자체 | 사내 미러 없으면 wheel 반입 절차. 나가는 건 패키지 요청뿐, 원문 아님 |

### 6.2 검증 필요한 내부 인프라 스펙

1. **JSON 구조화 출력 지원 여부** — facet 추출이 여기 의존. OpenAI-compatible이라도 `response_format`/json schema 지원은 불확실(Ollama `format: json`은 되지만 스키마 강제는 모델 의존). 미지원이면 프롬프트 + 관용적 파서 + 재시도로 내려가고, 실패율이 커버리지 리포트에 직접 반영된다.
2. **컨텍스트 길이 상한** — 청킹 설계를 결정.

## 〖 7. 실데이터 미접근 대응 〗

- 합성 회고 20~30건을 직접 작성(3단 준수 / 미준수 / 무내용 / CL4 서술형 각 케이스 포함)해 프롬프트·스키마 검증.
- 사내 실행자에게 코드 + 프롬프트 전달. 1차 실행 후 **클러스터 카드(제목·요약·확산도)와 커버리지 숫자만** 회수. 원문·실명 회수 없음 → 반출 제약 무관.

---

## 〖 8. 비용·실패 처리 〗

- 200명 × (요약 + 추출) ≈ 400~600콜. 1회성이므로 야간 배치로 레이트 리밋 회피 가능.
- 재시도 3회 후 폐기.
- **커버리지 리포트**를 산출물에 첨부: 폐기 목록 · `substantive: false` 비율 · `Other` 범주 비율. 커버리지가 낮으면 결과 신뢰도를 이 숫자로 방어한다.

---

## 〖 9. 산출물 〗

1. 역량 클러스터 카드 세트 — 제목 / 요약 / 확산도 / 준비도 구간
2. `pjt` × `cl_level` 교차표
3. 워크숍용 미결 질문 목록 — 데이터가 답하지 못한 것 = know-why 공백
4. 커버리지 리포트

## 〖 10. 미결 항목 〗

설계를 실제로 좁히는 값 (확인 필요):

- **산출물 형태·기한** — 문서 / 슬라이드 / 워크숍 자료
- **범위** — 요구사항은 "우리 팀", 데이터는 부서원 ~200명. 팀 = 부서인지
- **실명 표기 정책** — 산출물에서 개인 귀속 허용 여부·익명화 요구

없어도 진행 가능한 항목:

- 청중(상사 단독 / 팀 리더십 / 전 부서원)
- `pjt` 값 목록·카디널리티, CL별 인원 분포
- 실행 주체 및 재실행 가능 여부
- Heritage Archive 산출물(임베딩·유사도) 재사용 가능 여부
- 성공 기준 — "토론 촉발"의 판정 방법
