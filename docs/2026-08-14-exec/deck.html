3 · 과제 정의

목표 설정

요구는 팀 단위, 데이터는 개인 단위다.

자료 200건은 각자가 자기 프로젝트 맥락에서 쓴 개인·근미래 서술이다. 팀 차원의 방향은 여기에 직접 적혀 있지 않고, 200건을 종합해야 나온다.

Before — 사람이 종합할 경우
  • 기준 일관성 — 동일한 잣대로 판단하기 어렵다. 순서·피로도가 개입한다.
  • 소수 의견 소실 — 요약은 다수를 남기고 소수를 버린다.
  • 근거 추적 — 종합 결과에서 개별 원문으로 돌아가기 어렵다.
After — 파이프라인이 종합할 경우
  • 동일 기준 — 200건 전부에 같은 질문을 적용한다.
  • 소수 의견 보존 — 인원이 적은 카테고리를 별도 트랙으로 남긴다.
  • 역추적 — 모든 항목이 원문 인용을 함께 보관한다.
따라서 목표를 다음과 같이 설정했다
  1. 200건 전수를 동일 기준으로 처리한다
  2. 소수 의견을 별도로 보존한다
  3. 모든 결과를 원문 인용으로 역추적 가능하게 한다

처리 시간 단축이 목적이 아니다 — 사람이 하면 품질이 담보되지 않는 부분을 기계에 맡긴 것이다.

6 · 신뢰성 확보

코드가 수행 td_extract.py:54 · :56 · :86

자동 분석 결과를 그대로 신뢰할 수 없으므로 네 가지 장치를 두었다.

장치내용
①원문 대조 근거 문장이 자료 원문에 실제로 존재하는지 대조한다. 없으면 생성된 문장이므로 폐기한다.
②인용 복제 차단 정리 서술이 원문을 그대로 옮긴 것에 불과하면 폐기한다.
③항목 단위 폐기 위반 시 해당 항목만 버리고 재질의한다. 자료 한 건 전체를 버리지 않는다.
④처리 결과 공개 신호 없음·기타 건수를 함께 보고한다. 소수 인원 카테고리는 별도 트랙으로 보존한다.

결과적으로, 추출 단계 산출물의 모든 문장은 원문 대조를 통과한 것이다.

인원수가 곧 중요도는 아니다 — 소수 의견 트랙을 따로 두는 이유가 여기 있다.

실측 — 코드에서 직접 확인

LLM을 호출하는 세 단계 중 원문 대조 코드가 있는 곳은 두 곳이다.

단계원문 대조 코드의미
추출td_extract.py · 12건뽑은 문장이 원문에 있는지 대조
배정td_assign.py · 10건배정 근거를 인용으로 확인
분류 체계td_taxonomy.py · 0건대조할 원문이 존재하지 않는다
분류 체계 — 카테고리 명칭과 경계

모델은 당사 도메인 지식이 없다. 사내 용어를 일반 용어로 치환하거나 조직 감각과 맞지 않는 경계로 묶는다.

코드가 보는 것은 관계 구조의 형식적 정합성뿐 — 명칭의 타당성은 판정하지 못한다.

시점 판정 — 단기 / 장기

자료에 시점을 명시한 작성자가 거의 없다. 현재 값은 모델의 추정이며 원문으로 검증할 수단이 없다.

사례 — LLM 명칭 → 실제 용어

모델 성능을 높여 해결되는 문제가 아니다 — 판단 근거가 데이터에 없는 구조적 문제다.
