2. 과제 정의

요구와 데이터 사이의 간극
요구는 팀 단위이나, 데이터는 개인 단위다.

자료 200건은 각자가 자기 프로젝트 맥락에서 작성한 개인·근미래 서술이다. 팀 차원의 방향은 여기에 직접 적혀 있지 않으며, 200건을 종합해야 도출된다.

종합을 사람이 수행할 경우의 문제
문제내용
기준 일관성200건을 동일한 잣대로 판단하기 어렵다. 읽는 순서와 피로도가 결과에 개입한다.
소수 의견 소실요약은 본질적으로 다수를 남기고 소수를 버린다. 1~2명이 제기한 방향은 정리 과정에서 사라진다.
근거 추적종합 결과에서 개별 원문으로 되돌아가기 어렵다.
목표 설정
  1. 200건 전수를 동일 기준으로 처리한다.
  2. 소수 의견을 별도로 보존한다.
  3. 모든 결과를 원문 인용으로 역추적 가능하게 한다.

처리 시간 단축이 목적이 아니다. 사람이 수행할 때 품질이 담보되지 않는 부분을 자동화한 것이다. 반대로 자동화가 담보하지 못하는 부분은 9면에 별도로 기술하였다.

5단계 처리 절차
단계명칭처리 내용 산출물언어모델 사용
①추출자료 원문에서 과제·역량·방향을 항목화항목 목록약 200회

④집계카테고리별 인원·역량 확보 여부 산출집계표미사용
⑤정리열람 가능한 문서로 생성검토용 정리 문서미사용

총 언어모델 호출 약 1,000회. 전 단계를 사내망 언어모델로만 처리하였다. ④·⑤단계는 산술과 문서 생성이므로 실행할 때마다 결과가 동일하다.

단계별 중간 산출물 보관

각 단계의 결과를 모두 별도 보관한다. 특정 단계의 결과가 잘못되면 그 단계부터 다시 실행하며, 앞 단계는 재실행하지 않는다. 처리가 중간에 중단되어도 중단 지점부터 재개된다.

선행 조건

호출량이 가장 큰 구간은 ③ 배정이다. 분류 체계가 바뀌면 이 단계를 전부 다시 수행해야 한다. 따라서 분류 체계 확정이 선행되어야 한다. 이 점이 10면 검증 절차를 앞에 두는 이유다.

분류 체계 — 명칭과 경계

사용 모델은 당사 도메인 지식을 갖고 있지 않다. 사내 용어를 일반 용어로 치환하거나, 조직 감각과 맞지 않는 경계로 묶는 사례가 발생한다. 자동 검사가 확인하는 것은 항목 간 연결 구조가 형식적으로 어긋나지 않았는지까지이며, 명칭 자체의 타당성은 판정하지 못한다.

시점 판정 — 단기 / 장기

자료에 시점을 명시한 작성자가 거의 없다. 현재 값은 모델의 추정이며, 원문으로 검증할 수단이 없다.

사례

모델이 생성한 명칭  →  실제 사용하는 용어

이는 모델 성능을 높여 해결되는 문제가 아니다. 판단 근거가 데이터에 존재하지 않는 구조적 문제다. 따라서 이 두 지점은 처음부터 사람이 확정하는 것으로 설계하였다.

질의답변
결과가 틀리면 어떻게 아는가 모든 항목이 원문 인용까지 역추적된다. 탐색기 화면에서 즉시 확인할 수 있다.
왜 사람이 직접 읽지 않았는가 200건 전수를 동일 기준으로 판단하고 소수 의견까지 보존하는 것이 목적이다. 표본 검토로는 달성되지 않는다.
외부 유출 위험은 없는가 전 과정을 사내망 언어모델로만 처리하였다.
이 결과로 바로 의사결정이 가능한가 분류 체계 검증 전이므로 초안이다. 검증 후 확정본을 보고한다.
다시 수행하려면 비용이 얼마나 드는가 배정 재실행 기준 약 600~800회 호출이다. 검토 화면은 언어모델을 사용하지 않아 반복 비용이 없다.
