| 항목 | 내용 |
|---|---|
| 대상 | 부서원 약 200명 · CL2/CL3/CL4 · 1회성 작성 자료 |

- 오늘 보고는 완성된 결론이 아니라 진행 현황과 남은 절차에 대한 것이다.

## 3. 과제 정의

**표시 내용**

**요구는 팀 단위, 데이터는 개인 단위다.**

자료 200건은 각자가 자기 프로젝트 맥락에서 쓴 개인·근미래 서술이다.
팀 차원의 방향은 여기에 직접 적혀 있지 않고, 200건을 종합해야 나온다.

**종합을 사람이 수행할 경우의 문제**

| 문제 | 내용 |
|---|---|
| 기준 일관성 | 200건을 동일한 잣대로 판단하기 어렵다. 읽는 순서와 피로도가 결과에 개입한다. |
| 소수 의견 소실 | 요약은 본질적으로 다수를 남기고 소수를 버린다. 1~2명이 제기한 방향은 정리 과정에서 사라진다. |
| 근거 추적 | 종합 결과에서 개별 원문으로 되돌아가기 어렵다. |

**따라서 목표를 다음과 같이 설정했다**

1. 200건 전수를 **동일 기준**으로 처리한다
2. 소수 의견을 **별도로 보존**한다
3. 모든 결과를 **원문 인용으로 역추적** 가능하게 한다

**구두 보충**
- 처리 시간 단축이 목적이 아니다. 사람이 하면 품질이 담보되지 않는 부분을 기계에 맡긴 것이다.
- 반대로 기계가 담보하지 못하는 부분은 9장에서 따로 말씀드린다.

## 4. 처리 방식

**표시 내용**

**5단계 파이프라인**

| 단계 | 처리 내용 | 산출물 | LLM 호출 |
|---|---|---|---|
| ① 추출 | 자료 원문에서 과제·역량·방향 항목화 | `extracted.json` | 약 200회 |
| ② 분류 체계 | 유사 항목을 묶어 카테고리 정의 | `taxonomy.json` | 약 30회 |
| ③ 배정 | 추출 항목을 카테고리에 배정 | `assignments.json` | 약 600~800회 |
| ④ 집계 | 카테고리별 인원·역량 확보 여부 산출 | `aggregates.json` | 없음 |
| ⑤ 정리 | 열람 가능한 문서로 생성 | `workshop-input.md` | 없음 |

총 LLM 호출 약 1,000회. 전 단계 사내망 LLM으로만 처리.

**단계별 중간 산출물을 모두 파일로 남긴다.**
특정 단계의 결과가 잘못되면 그 단계부터 다시 실행할 수 있고, 앞 단계는 재실행하지 않는다.
중간에 중단되어도 중단 지점부터 재개된다.

**구두 보충**
- ④·⑤단계는 LLM을 쓰지 않는 산술·문서 생성이다. 결과가 매번 동일하다.
- 호출량이 큰 구간은 ③ 배정이다. 분류 체계가 바뀌면 이 단계를 다시 돌려야 하므로, 체계 확정이 선행되어야 한다.

## 5. 추출 단계

**표시 내용**

자료 한 건에서 네 가지를 뽑는다. **200건 전부에 동일한 질문을 적용한다.**

| 축 | 내용 |
|---|---|
| 미래 과제 | 앞으로 수행하려는 업무 (+ 시점: 단기/장기/불명) |
| 보유 역량 | 이미 확보했다고 서술한 역량 |
| 필요 역량 | 부족하거나 필요하다고 서술한 역량 |
| 지향 방향 | 전반적 방향 |

**항목마다 근거 문장을 함께 보관한다**

- `text` — 정리된 서술
- `quotes` — 그 서술의 근거가 된 **원문 그대로의 문장**

**내용이 없는 자료는 별도 표시한다.**
서술이 사실상 없는 자료를 임의 분류하지 않고 `신호 없음`으로 분리한다.

**구두 보충**
- 근거 문장을 함께 들고 가는 이유는 6장에서 설명한다. 이것이 검증 체계 전체의 출발점이다.
- 시점(단기/장기)은 작성자가 명시한 경우가 드물어 상당수가 추정값이다. 이 부분은 9장에서 다시 다룬다.

## 6. 신뢰성 확보

**표시 내용**

자동 분석 결과를 그대로 신뢰할 수 없으므로 네 가지 장치를 두었다.

**① 원문 대조**
근거 문장이 해당 자료 원문에 실제로 존재하는지 대조한다.
존재하지 않으면 생성된 문장이므로 폐기한다.

**② 인용 복제 차단**
정리 서술이 원문을 그대로 옮긴 것에 불과한 경우 폐기한다.

**③ 항목 단위 폐기**
①·② 위반 시 **해당 항목만** 버리고 재질의한다. 자료 한 건 전체를 버리지 않는다.
재질의 후에도 통과하지 못하면 유효 항목만 보존한다.

**④ 처리 결과 공개**
전체 대상 중 신호 없음 처리된 건수, 기타로 분류된 건수를 함께 보고한다.
소수 인원이 제기한 카테고리는 다수 집계에 흡수되지 않도록 별도 트랙으로 보존한다.

> **결과적으로, 추출 단계 산출물의 모든 문장은 원문 대조를 통과한 것이다.**

**구두 보충**
- ①·②는 코드가 자동으로 수행한다. 사람이 표본 검사하는 방식이 아니다.
- ④의 수치는 실행 결과가 나오면 그대로 공개한다. 처리하지 못한 비율을 감추지 않는 것이 전제다.

## 7. 중간 결과 ① — 과제 군집

**표시 내용**

추출된 미래 과제를 카테고리로 묶고, 부서·CL별 분포를 교차 확인한다.

**카테고리 카드 형식**

> **[[카테고리명]]** — [[N]]명
> 인용: "[[원문 발췌]]"
> 관련 부서: [[부서 목록]]

| 구분 | 값 |
|---|---|
| 도출 카테고리 | [[N]]개 |
| 최다 인원 카테고리 | [[명칭]] · [[N]]명 |
| 소수 의견 보존 | [[N]]건 |
| 신호 없음 | [[N]]명 |

**모든 수치는 개별 원문까지 역추적된다.**
"이 숫자의 근거가 무엇인가"라는 질문에 해당 인원의 원문을 즉시 제시할 수 있다.

**구두 보충**
- 아직 도메인 검증 전 상태의 결과다. 카테고리 명칭은 확정된 것이 아니다.
- 인원수가 곧 중요도는 아니다. 소수 의견 트랙을 따로 두는 이유가 여기 있다.

## 8. 중간 결과 ② — 시간 × 역량 확보 매트릭스

**표시 내용**

군집만으로는 순서가 나오지 않는다. 두 축을 얹어 배치한다.

| 축 | 정의 | 결정 주체 |
|---|---|---|
| 가로 — 시간 | 단기 · 중기 · 장기 | **사람이 확정** (초안은 자동 생성) |
| 세로 — 역량 확보 | 필요 언급 대비 보유 언급 비율 | 데이터가 결정 (고정) |

- 버블 크기 = 해당 카테고리를 언급한 인원수
- **좌상단 = 시급하나 역량 미확보** — 우선 검토 대상
- 우하단 = 역량은 확보되어 있으나 장기로 분류된 항목 — 시점 재검토 대상
- **역량 언급이 없는 카테고리는 축 밖 별도 표시** — 판정 불가로 두고, 확보로 처리하지 않는다

> 세로축이 의미하는 것은 "팀에 해당 역량이 있다"가 아니라
> **"확보했다고 쓴 서술이 부족하다고 쓴 서술보다 많다"**이다.

| 구분 | 값 |
|---|---|
| 단기 / 중기 / 장기 | [[N]] / [[N]] / [[N]] |
| 판정 불가 (축 밖) | [[N]]건 |

**구두 보충**
- 세로축을 인원수와 섞지 않았다. 인원수는 버블 크기가 이미 표현하므로 축에서 제외했다.
- 가로축은 초안일 뿐이다. 확정은 10장의 검증 절차에서 이뤄진다.

## 9. 한계

**표시 내용**

**자동 검증이 성립하는 구간과 그렇지 않은 구간이 나뉜다.**

| 구간 | 검증 | 근거 |
|---|---|---|
| 추출 · 배정 | 가능 | 대조할 원문이 존재한다. 생성된 문장은 코드가 폐기한다. |
| **분류 체계 명명 · 시점 판정** | **불가** | 원문에 정답이 존재하지 않는다. |

**분류 체계 (카테고리 명칭과 경계)**
사용 모델은 당사 도메인 지식을 갖고 있지 않다.
사내 용어를 일반 용어로 치환하거나, 조직 감각과 맞지 않는 경계로 묶는 사례가 발생한다.
코드가 검증하는 것은 관계 구조의 형식적 정합성뿐이며, 명칭의 타당성은 판정하지 못한다.

**시점 판정 (단기/장기)**
자료에 시점을 명시한 작성자가 거의 없다.
현재 값은 모델의 추정이며, 원문으로 검증할 수단이 없다.

**사례**
[[LLM이 생성한 명칭]] → [[실제 사용하는 용어]]

**구두 보충**
- 이는 모델 성능을 높여 해결되는 문제가 아니다. 판단 근거가 데이터에 없는 구조적 문제다.
- 따라서 이 두 지점은 처음부터 사람이 확정하는 것으로 설계했다.

## 10. 대응 — 도메인 검증 절차

**표시 내용**

**전수 검토는 하지 않는다. 자동 검증이 성립하지 않는 지점에만 사람이 개입한다.**

| 구분 | 대상 | 사유 |
|---|---|---|
| 사람이 확정 | 카테고리 명칭·경계 / 시점 구분 | 원문으로 검증 불가 |
| 확인만 | 추출 결과 | 원문 대조를 이미 통과 |
| 확인만 | 배정 결과 | 체계 확정 후에는 기계적 분류 |
| 불필요 | 집계·문서 생성 | LLM 미사용, 결과 재현성 있음 |

**진행 방식**

- 부서별 담당자 참석, 약 4시간
- 자동 생성된 분류 체계 초안을 검토·수정
- 시점 구분을 현업 기준으로 조정

**검토용 화면은 구축되어 있다.**

| 도구 | 용도 |
|---|---|
| 탐색기 | 특정 수치의 근거 원문 확인 |
| 매트릭스 | 전체 배치 조망 및 시점 조정 |
| 취합 화면 | 참석자 의견 수렴 |

세 화면 모두 LLM을 호출하지 않으므로 반복 실행 비용이 없다.

**구두 보충**
- 검토 대상은 카테고리 수십 개 수준이지 자료 200건이 아니다.
- 체계가 확정되면 배정·집계는 재실행만 하면 되고 추가 인력이 필요하지 않다.

## 11. 향후 계획

**표시 내용**

| 순서 | 내용 | 소요 |
|---|---|---|
| 1 | 부서 담당자 분류 체계 검토 | 4시간 |
| 2 | 확정 체계로 배정·집계 재실행 | 자동 처리 |
| 3 | 결과 검수 (담당자 개별 확인) | 별도 소집 없음 |
| 4 | 부서별 미래 과제 정리본 완성 | — |

**최종 산출물**

- 부서별 과제 군집 (카테고리별 인원·부서·CL 분포)
- 시간 × 역량 확보 매트릭스
- 소수 의견 목록
- 처리 커버리지 보고

**구두 보충**
- 산출물은 결론이 아니라 논의의 출발점으로 사용하는 것을 전제로 한다.
- 파이프라인 자체는 자료 종류에 종속되지 않으므로 다른 비정형 문서에도 동일하게 적용 가능하다. (질문 시에만)

## 예상 질문

| 질문 | 답변 |
|---|---|
| 결과가 틀리면 어떻게 아는가 | 모든 항목이 원문 인용까지 역추적된다. 탐색기에서 즉시 확인 가능하다. |
| 왜 사람이 안 읽었나 | 200건 전수를 동일 기준으로 판단하고 소수 의견까지 보존하는 것이 목적이다. 표본 검토로는 달성되지 않는다. |
| 외부 유출 위험은 | 전 과정 사내망 LLM으로만 처리했다. |
| 이 결과로 바로 의사결정 가능한가 | 분류 체계 검증 전이므로 초안이다. 검증 후 확정본을 보고한다. |
| 다시 하려면 비용이 얼마나 드나 | 배정 재실행 기준 약 600~800회 호출이다. 검토 화면은 LLM을 쓰지 않아 반복 비용이 없다. |
