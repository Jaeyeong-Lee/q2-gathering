# 내부망 실행·검토 가이드 — 미래 과제와 역량 지도

이 문서는 내부망 운영 에이전트용이다. `nebula`는 이전 `td_*` 산출물의 스키마를 덮어쓰지 않는 별도 패키지다. Python 3.10 이상, Linux 또는 macOS에서 실행한다. 런타임은 Python 표준 라이브러리만 사용한다. OS 파일 잠금에 `fcntl`을 사용하므로 Windows 네이티브는 지원하지 않는다.

## 운영 에이전트의 실행 순서와 종료 조건

1. 아래 합성 실행을 완료하고 `status.json`이 complete인지 확인한다. `nebula.html`의 다섯 장면이 모두 그려지고, `matrix.html`의 버블에서 원문이 열리고, `review.html`에서 결정 JSON을 내려받을 수 있으면 환경 준비 완료다.
2. 입력 계약에 맞는 원문·PJT·네트워크를 준비한다. 중복 ID나 모집단 불일치가 있으면 입력을 고친 뒤 진행한다.
3. 내부 endpoint를 설정해 실입력을 처리한다. 실패하면 상태의 stage/call_key와 해당 단계 가이드를 확인하고 같은 명령으로 재개한다. complete와 최종 HTML이 모두 생성되어야 추출 실행 완료다.
4. 검토 단계에서 원문·시간·과제 분류·역량 연결을 확인한다. 수정이 필요하면 corrections로 재실행하고, 변경된 run_id에 대한 검토를 새로 저장한다.
5. 승인 파일로 `--approved-only` 빌드 후 표시 과제와 원문을 확인한다. 내부 검토되지 않은 초안 화면을 실제 결과 검증 완료로 보고하지 않는다. 모델 의미 검증과 오프라인 발표 리허설을 끝낸 뒤 최종 산출물 경로와 run_id를 보고한다.

## 1. 먼저 합성 자료로 실행

저장소 루트에서 다음 명령을 실행한다. API 키·네트워크가 필요 없다.

```sh
python3 -m nebula demo --out data/nebula-demo
```

`data/nebula-demo/nebula.html`이 메인 발표 화면이다. 하단 자동 발표로 사람 → 과제 → 성운 → 시간 → 역량의 다섯 장면을 재생한다. `matrix.html`은 시간 × 보유·필요 역량의 2차원 탐색 화면, `review.html`은 검토·수정 화면이다. 세 화면은 같은 실행 결과를 사용한다. 파일을 직접 브라우저로 연다. 브라우저에는 LLM 호출이나 외부 자산 요청이 없다. 입력·분류가 합성이라는 표시가 나온다. 합성 데모는 자체 텍스트의 TF-IDF 코사인으로 만든 예시 네트워크를 입력 어댑터에 전달한다. 실제 실행에서는 제공된 네트워크만 사용한다. 이 경로의 stub은 인터페이스 검증용이며 실제 모델 품질을 증명하지 않는다.

## 2. 실입력 계약

`persons.json`은 아래 형태의 배열이다. 예시는 합성이다.

```json
[
  {
    "id": "P001",
    "name": "합성 인물 001",
    "pjt": "테스트 개발",
    "text": "단기적으로 검증 절차를 개선하고 싶다. 이 과제에는 기존 로그 분석 경험을 활용하려 한다. 이를 위해 실험 설계 역량이 더 필요하다."
  }
]
```

- `id`: 비어 있지 않은 문자열 또는 정수. 정수는 문자열로 정규화한다. 정규화 후 중복이면 실패한다. 이름으로 결합하지 않는다.
- `name`: 선택적인 표시명. 없으면 ID를 표시한다.
- `pjt`: 필수 문자열. 8개를 코드에 고정하지 않는다. 다른 코드의 `pjt`가 상위 3조직이고 실제 8개 조직이 `part`에 있다면 운영자가 올바른 대응으로 입력을 준비한다.
- `text`: 비어 있지 않은 사람별 원문. 빈 텍스트는 입력 오류다. 내용이 일반적인 다짐뿐인 문서는 허용하며 추출 과제가 0개일 수 있다.
- 1인 원문은 기본 24,000자 이하. 넘으면 자동으로 자르지 않고 중단한다. 모델 입력 한도를 확인한 뒤 `--max-chars`를 조정한다. 원문은 추출 기간 동안 변경하지 않는다.

## 3. 기존 유사도 네트워크

`--network`는 선택 사항이다. 없으면 사람 유사도를 만들었다고 주장하지 않고 화면에서 미제공으로 표시한다. 두 형식을 지원한다.

기존 neighbors 형식:

```json
{"P001":[{"id":"P002","similarity":0.81}],"P002":[{"id":"P001","similarity":0.81}]}
```

좌표까지 보존하는 형식:

```json
{
  "nodes":[{"id":"P001","x":0.2,"y":0.7},{"id":"P002","x":0.8,"y":0.4}],
  "edges":[{"a":"P001","b":"P002","similarity":0.81}]
}
```

명시적인 nodes를 제공하면 입력 인물 전원을 포함한다. 좌표는 전원 제공하거나 전원 생략한다. 좌표가 없으면 표시용 배치를 사용하며 새 유사도 계산으로 설명하지 않는다. 점수는 [-1,1]의 유한한 수여야 한다. 알 수 없는 인물, 자기 연결, 충돌하는 양방향 점수는 거부한다. 기존 네트워크의 모집단이 더 넓다면 입력 인물 집합으로 먼저 제한해 준비한다.

## 4. OpenAI 호환 연결

```sh
export NEBULA_BASE_URL=http://INTERNAL_HOST:PORT/v1
export NEBULA_MODEL=INTERNAL_MODEL_ID
export NEBULA_API_KEY=INTERNAL_KEY
export NEBULA_TIMEOUT=120
export NEBULA_MAX_TOKENS=8192
export NEBULA_JSON_MODE=json_object

python3 -m nebula run \
  --input /secure/inputs/persons.json \
  --network /secure/inputs/neighbors.json \
  --out /secure/runs/nebula-001
```

주소·모델은 실제 내부 값으로 설정한다. `BASE_URL`은 `/chat/completions` 앞까지다. 기본 외부 endpoint는 없다. 요청은 비스트리밍 Chat Completions 형식이며 API 키가 있으면 Bearer 헤더를 보낸다. temperature를 강제하지 않는다. 사내 서버가 `response_format`을 지원하지 않으면 `NEBULA_JSON_MODE=none`으로 설정한다. 이 경우에도 프롬프트는 JSON만 요구하고 응답을 검증한다. HTML은 endpoint나 키를 필요로 하지 않는다. HTTPS 사내 CA는 Python의 신뢰 저장소 또는 `SSL_CERT_FILE`로 설정하며 인증서 검증을 끄지 않는다. redirect는 인증 정보 전달을 막기 위해 거부한다.

## 5. 처리 단계와 프롬프트

`nebula/prompts.py`에 원문 추출, PJT taxonomy 초안, taxonomy 정리, 과제 배정 프롬프트가 분리되어 있다. 원문은 지시문이 아닌 데이터라는 지침을 포함한다.

- 추출은 1인 단위다. 미래 업무와 학습 필요를 구별하며, 막연한 방향을 구체적인 계획으로 바꾸지 않는다.
- 단기·중기·장기를 표시하려면 과제 전체 인용과 해당 시간 표현을 함께 담은 정확한 원문 인용이 필요하다. 날짜·연도·난도만으로 기간을 추측하지 않는다. 그런 표현은 원문에서 확인하되 화면 시간은 미명시로 남긴다.
- 역량은 자기서술이다. `have`와 `need`는 기존 용어의 `capability_have`와 `capability_gap`에 대응한다. 이 패키지의 축 구분이며 측정된 수준이 아니다.
- 관계 인용은 과제 인용과 역량 인용 양쪽을 포함한 연속 원문이어야 한다. 단순한 문서 내 동시 출현은 연결 근거가 아니다. 구조 검증만으로 의미적인 연결을 입증하지 못하므로 반드시 내부에서 검토한다.
- PJT별로 기본 24개 과제씩 초안 분류를 확장한다. 정의·포함·제외 기준을 저장하고 별도 정리 호출에서 최종 카테고리를 만든다. 정리 호출은 정의 전체와 제한된 대표 과제를 사용한다. 희소 과제가 잘못 합쳐지지 않았는지 검토한다.
- 최종 정의를 기준으로 과제를 다시 배정한다. 하나의 과제에는 카테고리 하나 또는 null(미분류)만 허용한다. 응답에서 일부 과제가 빠지면 중단한다.
- AX 관찰은 미래 과제 원문 인용의 표현에서 계산하며 별도 카테고리나 역량 점수로 취급하지 않는다.

## 6. 실패·재개와 출력물

동일 명령을 다시 실행한다. 검증을 통과한 각 호출 결과만 `cache/`에 원자적으로 저장된다. 캐시 키에는 입력·모델·endpoint·프롬프트·계약 버전이 들어간다. API 키는 캐시 키나 산출물에 기록하지 않는다.

HTTP 408·429·5xx와 연결/타임아웃은 호출당 최대 3회로 제한한다. 401/403 등은 즉시 실패한다. JSON 파싱·스키마·인용 오류는 완료로 저장하지 않는다. 출력 토큰 잘림은 명시적으로 실패하며 `MAX_TOKENS` 또는 배치 크기를 조정한다. 기본 응답은 비스트리밍이므로 서버의 스트리밍 전용 모드는 지원하지 않는다.

동일 출력 디렉터리에 동시 실행하면 잠금 오류로 실패한다. 서로 다른 out은 독립 실행할 수 있다. 재실행을 시작하면 직전 HTML은 `nebula.previous.html`, `matrix.previous.html`, `review.previous.html`로 보존한다. 새 실행이 실패한 상태를 기존 성공 화면으로 오인하지 않도록 현재 이름의 HTML은 완료 빌드에서만 생성한다.

주요 파일:

- `status.json`: running/failed/complete, 실패 단계·호출 키·완료 호출 수·캐시 수 등 상태. 원문 없는 운영 진단에 우선 사용한다.
- `result.json`: 원문·추출·카테고리·배정·네트워크를 묶은 불변 스냅샷. 직접 수정하지 않는다.
- `corrections-template.json`: 추출/분류를 수정할 때의 전체 입력 초안.
- `applied-corrections.json`: 마지막 성공 실행에 적용한 사람·taxonomy 정정 누적 상태. 직접 편집하지 않고 corrections 입력으로 변경한다.
- `task-inputs/`, `taxonomy-drafts/`: PJT 단계가 한도에 걸렸을 때 내부 검토에 사용할 중간 결과.
- `view.json`, `nebula.html`, `matrix.html`, `review.html`: 실제 내용이 포함된 민감 결과.
- `nebula.html`: 발표용 다섯 장면 화면. `#scene=0`~`#scene=4`로 특정 장면을 직접 열 수 있고, `pjt`·`category`·`task`·`person`도 같은 방식으로 붙는다. 리허설 중단 지점을 그대로 공유할 때 쓴다.

`--batch-size`는 한 요청의 과제 수를 줄인다. `--max-chars`는 문자 기반 가드이며 토큰 계산기가 아니다. 누적 taxonomy를 포함한 요청도 별도로 제한한다. 초과 시 조용히 내용을 자르지 않는다. 큰 PJT는 분류 초안을 검토해 corrections의 taxonomies로 제공하거나, 모델 한도를 확인한 후 가드를 조정한다.

## 7. 검토와 수정

`review.html`에서 과제 원문·시간 근거·배정 이유·역량 연결·전체 회고를 비교한다. 과제 단위로 승인/제외/미검토와 메모를 저장하고 `review.json`을 내려받는다. 카테고리를 바꾸면 같은 PJT 안의 카테고리 또는 미분류만 가능하며 수정 메모가 필요하다. 한 과제의 승인은 표시되는 추출·시간·배정·역량 연결을 함께 확인했다는 의미다.

추출 자체가 틀렸다면 사람별 추출 JSON 편집을 사용해 `corrections.json`을 내려받는다. 모양은 다음과 같다.

```json
{"persons":[{"person_id":"P001","source_hash":"원래 제공된 값 유지","extraction":{"tasks":[],"capabilities":[],"links":[]}}]}
```

실제 편집은 제공된 템플릿의 항목을 수정한다. `ref`는 한 사람 안에서 고유한 임시 참조, `occurrence`는 해당 인용의 1부터 시작하는 출현 번호다. 임의의 최종 ID를 작성하지 않는다. 인용은 공백·개행까지 정확해야 한다. 연결되지 않은 역량을 삭제할 필요는 없다. source_hash가 다르면 현재 원문에서 다시 검토한다.

```sh
python3 -m nebula run \
  --input /secure/inputs/persons.json \
  --network /secure/inputs/neighbors.json \
  --corrections /secure/review/corrections.json \
  --out /secure/runs/nebula-001
```

같은 out에서 정정은 누적된다. A를 수정한 다음 B만 포함하는 파일로 재실행해도 A의 정정을 유지한다. `--corrections`를 생략해도 마지막 성공 실행의 정정을 유지한다. 검토 화면의 추출 정정 내보내기는 기존에 적용한 사람 정정도 포함한다. 화면의 정정 취소는 이번 편집을 취소하며 과거에 적용된 정정을 지우지 않는다.

모든 누적 정정을 버리고 모델 추출·분류 기준으로 돌아가려면 같은 run/demo 명령에 `--reset-corrections`를 추가한다. 함께 제공한 새 corrections는 초기화 후 적용한다. 검증된 모델 캐시는 유지하므로 새 모델 호출을 강제하는 옵션은 아니다. 원문 해시가 바뀌거나 사람이 제거되면 해당 사람의 이전 정정은 재사용하지 않는다. PJT 과제 해시가 바뀌면 해당 taxonomy 정정도 재사용하지 않고 새로 분류한다. 명시적으로 제공한 corrections의 해시가 오래되었으면 오류로 중단한다. 실패한 실행은 마지막 성공 정정 상태를 교체하지 않으므로 고친 입력과 정정 파일을 다시 제공한다.

수정되지 않은 사람 추출은 캐시를 사용한다. 바뀐 결과에 의존하는 분류/배정은 재계산한다. 결과 run_id가 바뀌면 과거 review.json은 거부한다.

taxonomy는 `corrections-template.json`의 taxonomies에서 수정할 PJT만 남겨 `name/definition/includes/excludes`를 편집한다. `pjt`, `input_hash`는 유지한다. 사람 추출 변경으로 해당 PJT 과제가 바뀌었다면 이전 taxonomy input_hash를 강제로 고쳐 쓰지 말고 새 과제 집합을 다시 검토한다. 사람만 수정하는 파일에는 이전 taxonomies를 포함하지 않는다.

## 8. 최종 승인 화면 생성

```sh
python3 -m nebula build \
  --out /secure/runs/nebula-001 \
  --review /secure/review/review.json \
  --approved-only
```

이 명령은 LLM을 호출하지 않는다. 승인된 과제만 버블 집계에 들어간다. 기본 빌드는 미검토 결과도 포함하는 탐색 초안이며 제외된 과제는 표시하지 않는다. 승인된 과제가 없으면 빈 상태를 명시한다. 원문·미연결 역량·명부가 파일에 포함될 수 있으므로 승인 화면도 반출용 자료가 아니다.

## 9. 내부 의미 검증 기준

자동 테스트와 JSON 검증이 추출의 의미를 보장하지 않는다. 성격이 다른 PJT와 작성 양식에서 다음을 확인한다.

- 업무 과제와 학습 필요를 혼동하거나 구체성을 추가했는가?
- 핵심 미래 과제를 빠뜨렸는가? 시간 표현의 주체가 맞는가?
- 보유 경험을 과장하거나, 필요 역량을 모델이 추측했는가?
- 인용이 존재하더라도 실제로 해당 과제와 역량을 연결하는가?
- 같은 카테고리의 과제들이 업무 대상과 목적 면에서 함께 읽힐 만한가?
- 분류 정리 단계에서 PJT의 고유·희소 과제가 사라졌는가?

실제 발표 사례는 모두 근거를 확인한다. 검토 메모와 원문은 내부에 보관한다. 수행 가능성·투자 우선순위·실행 순서는 별도 사람의 판단이다.

## 10. 보안과 전달

실입력은 내부 endpoint에서만 처리한다. 캐시·corrections·JSON·HTML에는 이름보다 민감한 카테고리·전략 표현도 들어갈 수 있다. 출력은 별도의 내부 폴더에 두고 Git에 추가하지 않는다. `dist` 아래 출력은 코드가 거부한다. 익명화와 승인 표시가 공개 허용을 뜻하지 않는다. 파일은 원자적으로 기록하며 새 산출물 권한은 소유자 읽기/쓰기다. 진단 시 외부로 전달할 것은 상태와 오류 코드에 한정한다.

## 11. 개발 검증

```sh
python3 -m pytest tests/test_nebula_pipeline.py tests/test_nebula_network.py tests/test_nebula_http.py
python3 -m mypy nebula --check-untyped-defs
```

HTTP 테스트는 로컬 호환 서버로 수행하며 실제 LLM에 연결하지 않는다. JSON 형태·인증·재시도 계약을 확인한다. 전체 저장소 테스트에는 기존 프로젝트 개발 의존성이 필요하다. 사용자 인터페이스의 브라우저 검사 명령은 `tests/nebula_browser.cjs` 상단을 참조한다. 동일 환경에서 `node tests/nebula_presentation.cjs`는 과제 0개·승인 0개·자동 발표·첫 사람 선택·원문과 승인 표기·특수문자 PJT를 추가 검증한다.


## 12. 코드 수정 지점

| 목적 | 파일 | 유지할 계약 |
| --- | --- | --- |
| 명령·옵션·실행 순서 | `nebula/__main__.py` | 한 out의 전체 작업 잠금, 실패 상태 기록 |
| 추출·분류·재개·정정·승인 | `nebula/pipeline.py` | PJT 독립 분류, 누적 정정, run_id 일치 |
| 입력·근거·응답 검증 | `nebula/model.py` | 정확한 인용, 안정적인 ID, 누락 배정 거부 |
| 모델 지침 | `nebula/prompts.py` | 업무·역량 구별, 명시적 시간, 직접 연결 근거 |
| 내부 모델 HTTP | `nebula/llm.py` | OpenAI 호환 JSON, 제한된 재시도, 비밀정보 제외 |
| 캐시·잠금·파일 | `nebula/storage.py` | 검증된 응답만 캐시, 파일 단위 원자적 교체 |
| 기존 네트워크 입력 | `nebula/network.py` | 사람 ID로 결합, 점수·좌표 보존 |
| 집계·HTML 생성 | `nebula/render.py` | 고유 인원 집계, 안전한 JSON 삽입 |
| 발표 화면 페이로드 | `nebula/render.py` `build_nebula` | 사람·PJT 색인과 원래 ID 병기, 미분류 보존 |
| 발표 UI | `nebula/templates/nebula.html` | 다섯 장면, 좌표 유무 표기, 장면 딥링크 |
| 탐색·검토 UI | `nebula/templates/` | 오프라인 동작, 원문 접근, 정정 내보내기 |
| 합성 자료 | `nebula/demo.py` | 실제 조직 데이터와 명확히 구별 |

발표 화면이 어떤 계약 차이를 넘어 파이프라인에 붙었는지는 [[nebula-handoff-2026-09-11]]에 있다. 템플릿의 색인·중기·미분류·좌표 부재 처리를 건드리기 전에 읽는다.

프롬프트를 바꾸면 해당 호출의 캐시 키가 바뀐다. 사람·taxonomy의 기존 수동 정정은 명시적으로 초기화하기 전까지 우선하므로 모델 변경을 비교할 때는 새 out을 사용한다. 입력부터 재개·정정·승인까지의 계약 테스트는 `tests/test_nebula_pipeline.py`, HTTP는 `tests/test_nebula_http.py`, 네트워크는 `tests/test_nebula_network.py`, 실제 파일 내보내기와 재빌드는 `tests/nebula_browser.cjs`에서 확인한다.


## 13. 내부 모델 결과가 부정확할 때

실행 성공과 추출 품질은 별도다. status가 complete라도 내부 원문 표본으로 먼저 검토한다. 형식 오류인지 의미 오류인지 구분한 뒤 수정한다.

- JSON 오류·필드 누락: 해당 stage와 call_key를 확인한다. `NEBULA_JSON_MODE` 지원 여부와 출력 토큰 한도를 점검한다. 완료되지 않은 응답은 캐시에 들어가지 않는다.
- 원문 인용 오류: 정확한 공백·개행 포함 인용이 필요하다. 추출 프롬프트를 조정하거나 사람별 정정을 입력한다. 검증을 느슨하게 만들어 통과시키지 않는다.
- 과제 누락·창작·잘못된 역량 연결: 구조 검증으로 해결할 수 없다. 검토 화면에서 추출 JSON을 수정하고 재실행한다. 모델/프롬프트 비교에는 동일한 소수의 원문 표본과 서로 다른 out을 사용한다.
- 카테고리 과잉 통합: PJT별 taxonomy 초안·정의·포함/제외 기준을 확인하고 taxonomy 정정으로 반영한다. 단순히 범주 수를 고정하지 않는다.

발표 화면에는 과제의 승인 상태, 시간 근거, 역량 인용과 연결 근거가 함께 표시된다. 과제나 승인 결과가 0개면 빈 상태를 표시한다. 이는 검증 오류로 중단된 실행을 대신하는 결과가 아니다. 실패한 실행은 status가 failed이며 기존 HTML은 previous 이름으로 보존된다.
