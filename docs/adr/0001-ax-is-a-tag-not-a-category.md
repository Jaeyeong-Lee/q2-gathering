# AX는 카테고리가 아니라 카드의 직교 태그다

AX(AI Transformation)가 조직의 화두라 회고에 언급이 몰리는데, 그대로 두면 taxonomy가 "AX 기반 테스트 지능화"
같은 **카테고리 하나**를 만들어 Yield·Auto Diag·BIB 과제를 원래 도메인 카테고리에서 뜯어간다(합성 실행
`dist/wiki_memtest/cluster-02.md`에서 실제로 34명이 그렇게 빨려들어갔고, 같은 실행의 `index.md`는 AX를
"개별 과제를 관통하는 상위 축"이라 적었다 — 같은 산출물 안에서 축이자 카테고리다). 그래서 AX는
`future_task` 항목에 붙는 **플래그**(`ax_mentioned`)로 두고, 카테고리 자리에서 도메인과 경쟁시키지 않는다.

## Considered Options

- **별도 축 `ax_task[]`로 분리** — 기각. `future_task`에서 AX 건을 빼내면 그 항목이 도메인 카테고리 집계에서
  사라져 `people`이 줄어든다. 카테고리가 AX를 잡아먹는 문제를 방향만 바꿔 되풀이한다.
- **LLM에게 "진짜 AX인가"를 판정시키기** — 기각. 화두라서 붙은 수사를 걸러내고 싶은 욕구는 진짜지만, 그
  판정은 방어할 근거가 없다. `confidence` 필드를 스키마에서 뺀 것과 같은 이유다. 파이프라인은 **원문에
  적혔다는 사실만** 기록하고("누가 AX라고 말했나"), 실체 판정은 워크숍에서 사람이 한다.
- **`capability_gap`에도 태그** — 기각. 소비처가 없다.

## Consequences

- 태그는 `quotes`만 보고 붙는다. `text`는 LLM이 고쳐 쓴 서술이라 원문에 없던 "AI"가 끼어들 수 있다.
  대신 인용이 AX 표현 없는 문장으로 잡히면 **놓친다** — 의도된 누락이다.
- **taxonomy가 AX 카테고리를 만드는 것 자체는 이 결정이 막지 못한다.** 태그는 카드 층의 장치이고,
  카테고리 생성을 막으려면 `td_taxonomy`/`td_assign` 프롬프트에 별도 지시가 필요하다(미결).
