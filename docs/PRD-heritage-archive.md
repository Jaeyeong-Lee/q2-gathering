# PRD: 2분기회 AI 세그먼트 — Heritage Archive

## Problem Statement

- 사내 분기 전체회의(200명, 비개발자 다수)에서 Jay가 10분간 AI 세그먼트를 진행해야 함
- 목적은 교육이 아니라 경험/오락 — 딱딱한 AI 데모는 반응이 식음
- 부서원 150명이 작성한 "근원경쟁력" 회고 자료가 있지만, 활용되지 않고 묻혀있음
- 세그먼트 종료 후에도 이 자료를 다시 탐색할 방법이 없음 — 일회성 이벤트로 소비되고 끝남
- AX 조직의 존재감을 슬라이드 홍보 없이, 경험 자체로 자연스럽게 각인시켜야 함

## Solution

- 150명의 근원경쟁력 텍스트를 임베딩·유사도·태그·빈도로 가공해 "Heritage Archive"라는 정적 단일 HTML 배포물을 제작
- 무대에서는 워드클라우드 리빌 → 유사도 네트워크(에고 뷰) → 빈도 퀴즈(Higher/Lower) → 클로징의 4단 에너지 곡선으로 10분 진행
- Archive는 발표 이후에도 사내 GitHub Pages에 상시 공개되어, 참석자가 스스로 자기 이름을 검색하고 닮은 동료를 탐색 가능
- 모든 계산은 빌드 타임에 완료(런타임 API 호출 zero) — 강당 네트워크 리스크 제거, 발표 당일 로컬 백업 가능

## Implementation Decisions

- **배포 형태**: 정적 단일 HTML. 모든 데이터(JSON)와 라이브러리(wordcloud2.js 등)는 인라인 권장 — 외부 의존성 최소화
- **호스팅**: 사내 GitHub Pages + 발표 당일 로컬 파일 백업 병행. 모바일 대응 불필요(현장 QR 오픈 안 함)
- **런타임 API 호출 zero 원칙**: 임베딩, 유사도, 태그 추출은 전부 빌드 타임에 완료. 무대/브라우저에서는 사전 계산된 JSON만 읽음
- **역할 분담**: Jay는 PPT 파싱 + 임베딩 API 호출 담당. Claude/에이전트는 형태소·태그·유사도 변환 스크립트 및 Archive HTML 담당
- **기존 프로토타입 기반**: `similarity-network-prototype.html`(force-directed 캔버스, 팀 필터, Top-N 슬라이더, 에고 뷰 순차 리빌)을 확장 — 신규 개발 아님
- **워드클라우드 합산 로직**: 인당 단어 빈도 딕셔너리를 JSON에 사전 저장 → 브라우저에서 선택 집합에 대해 단순 덧셈 후 wordcloud2.js로 재렌더. 150명×수백 단어 규모라 성능 이슈 없음. 합산 최소 인원 5명 미만 시 렌더 회피/경고
- **태그 시스템**: 인물 디테일 패널의 태그 칩 + 태그 필터(팀 필터와 동일 dim/점등 UX) + 에고 뷰 엣지의 공통 태그 라벨(공통 태그 있을 때만 표시). 태그를 노드로 만드는 이분 그래프 구조는 채택하지 않음(헤어볼 우려)
- **태그 추출 파이프라인**: 1인 1호출 × 150회 배치(긴 컨텍스트 1회 호출 방식 아님) → 자유추출 + 동의어 병합 수준의 간단 정규화만 적용 → 태그 풀 전체를 1~2회 LLM 호출로 최종 정리. 정식 2-pass vocabulary/계층화/온톨로지는 v2로 이관
- **데이터 인터페이스** (확정):
  ```
  persons.json: {
    id,          // PPT 파싱 순번 기반 생성 (PPT 원문에 id 없음, 이름 중복 대비 필수)
    name,
    pjt,         // team → pjt로 변경. 프로젝트 단위 구분자
    cl_level,
    text,        // 회고 원문 전체(md). freq/tag 추출 소스이자 인물카드 렌더 소스
    tags: [...]
  }
  neighbors.json: { [id]: [{ id, similarity }, ...] }  // 인당 top-K, K는 build config 상수
  freq.json:      { [id]: { 단어: 횟수 } }
  ```
- **이웃 수(K) 관련 3계층 변수화** (모두 build-time config, 하드코딩 금지):
  - **K (저장 이웃 수)** = 30. neighbors.json 생성 시 인당 상한. 성능 병목은 인원수(150, O(n²) 반발력 계산)에서 오고 K와 무관하므로 12→30 확장에 따른 성능 저하 없음(엣지 draw call 900→4500개 수준은 캔버스에서 체감 차이 없음)
  - **EGO_DISPLAY_N (에고 뷰 표시 수)**: 기존 프로토타입 하드코딩 10 → 상수화, K 이하로 제한
  - **Top-N 슬라이더 (오버뷰 엣지 수)**: 기존 프로토타입에 이미 2~12 슬라이더 존재. 슬라이더는 저장된 top-K 배열을 상위 N개로 슬라이싱만 하는 방식(매 프레임 재계산 아님) → 상한을 K(30)까지 확장 가능
  - 관계: K ≥ EGO_DISPLAY_N ≥ Top-N 슬라이더 최대값
  - 임베딩은 인당 1벡터(2~3페이지 합산) 권장. 벡터 차원수는 사내 임베딩 API 스펙 확인 필요
- **배포 산출물 조립**: 빌드 스크립트가 persons/neighbors/freq JSON 생성 → Archive HTML 빌드 시 `<script>` 태그로 전량 인라인 → 외부 파일 참조 없는 단일 정적 .html 하나로 완성 (GitHub Pages 업로드·로컬 백업 모두 이 파일 하나)
- **인물 카드**: 인당 회고 텍스트(md) 렌더만 포함. PPT 페이지 이미지 export는 스코프 제외
- **작성할 코드 4종**:
  1. 형태소/빈도 집계 스크립트 (kiwipiepy 등, 명사 위주, 커스텀 불용어)
  2. 태그 추출 배치 스크립트 (150콜 루프 + 프롬프트 + 정규화 후처리)
  3. 코사인 유사도 → top-12 이웃 JSON 변환 스크립트
  4. Archive HTML 확장 (기존 프로토타입 + 워드클라우드 + 태그 + 인물 카드 통합)
- **RAG는 무대 라이브 데모 없음** — 클로징에서 소개만. RAG 자체는 별도 사내 UI로 이미 존재, 본 프로젝트 스코프 밖

## Testing Decisions

- 외부 행동(입력 → 출력 데이터 구조)만 검증하고, 내부 구현 디테일(루프 방식, 변수명 등)은 테스트하지 않음
- **형태소/빈도 집계 스크립트**: `텍스트 → freq JSON` 순수 함수 단위 테스트. 불용어 필터링이 올바르게 적용되는지, 한글 명사 추출이 정확한지 검증
- **태그 추출 배치 스크립트**: LLM 호출부는 목킹(mocking)하고, `LLM 응답 → 정규화된 태그 배열` 변환 로직만 순수 함수로 테스트. 개별 호출 실패 시 재시도 로직 별도 검증
- **유사도 변환 스크립트**: `임베딩 벡터[] → top-12 이웃 JSON` 순수 함수 테스트. 코사인 유사도 계산 정확성, top-12 정렬/컷오프 검증
- **Archive HTML**: 렌더 로직을 DOM 직접 조작과 분리해 `데이터 JSON → 렌더 상태` 형태의 순수 함수 단위로 테스트. 기존 프로토타입에 이미 있는 force-directed 물리 연산·에고 뷰 리빌 로직은 회귀 없는지 위주로 확인
- 프로젝트 내 기존 테스트 프레임워크/prior art 없음 — 신규 스크립트이므로 각 언어 표준 테스트 러너(예: Python이면 pytest) 채택 권장
